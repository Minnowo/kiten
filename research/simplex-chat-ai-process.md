# SimpleX Chat: documentation layers and plans for agent-driven development

- **Sources:** files from https://github.com/simplex-chat/simplex-chat,
  shallow clone of commit `479548e` (2026-10-03), fetched 2026-10-14:
  - `docs/CONTRIBUTING.md` (revision 2025-07-25)
  - `docs/contributing/CODE.md`, `docs/contributing/PROJECT.md`
  - `apps/ios/CODE.md`, `apps/multiplatform/CODE.md`
  - `apps/ios/{product,spec}/`, `apps/multiplatform/{product,spec}/`
  - `plans/` (114 files)
  - A web search found no blog post or public write-up about the process;
    everything here comes from the repository itself.
- **What it is:** A privacy-focused messenger with a Haskell core, SwiftUI iOS
  app and Kotlin Multiplatform Android/desktop app. The repo documents its
  development process for LLM agents in detail: contributor rules written to
  double as agent instructions, a three-layer product/spec/source
  documentation system that acts as the agent's memory across sessions, and
  a plan file stored in the repo before each change.
- **Relevant when:** writing agent instruction files; large multi-platform
  codebases where agents lose context between sessions; security-sensitive
  code (protocols, crypto, messaging); projects that want an in-repo record
  of design decisions; deciding how much documentation to keep agents in sync
  with.
- **Used in this kit:** nothing yet.

## 1. Contributor docs that double as agent instructions

`docs/CONTRIBUTING.md` says the contributor docs "can be used with LLM
prompts". It gives a ready-made `CLAUDE.md` for contributors to create
locally; the repo does not commit one:

```markdown
@README.md
@docs/CONTRIBUTING.md
@docs/contributing/PROJECT.md
@docs/contributing/CODE.md
```

App contributors also import `apps/multiplatform/README.md` or
`apps/ios/README.md`. Humans and agents follow the same rules from the same
files.

Rules in `CONTRIBUTING.md` and `docs/contributing/CODE.md` (shared with the
`simplexmq` repo):

- **User problems only.** "We do not make code changes to improve code - any
  change must address a specific user problem or request."
- **Discuss plans early**, before contributing.
- **Security.** Apply adversarial thinking ("what may happen if one of the
  communicating parties is malicious") and write an explicit threat model for
  each change.
- **Minimal diffs.** Never rename variables, parameters or functions unless
  the rename is the point of the change. Never move existing code or document
  sections. Refactor only when it "substantially reduces cost of solving the
  current problem, including the cost of refactoring".
- **Comments.** No comments that restate the code; comment only non-obvious
  design decisions; "Assume a competent Haskell reader".
- **Types.** Types reflect business meaning, not data shape: two
  constructors that mean different things are not merged into one with a
  `Maybe` field just because the data overlaps. Duplicate pattern-match arms
  are fine; duplicate function bodies are not (parameterize a shared helper
  instead).
- **Analysis.** Trace data flows end to end; flag values that are discarded
  and rebuilt from partial data ("usually a bug"); read the implementation of
  every called function, not just its signature. "Do not save time on
  analysis."

`PROJECT.md` is a short orientation file: module map, migration procedure
(including "`chat_schema.sql` is auto-generated by tests - do not edit"),
test layout, and build commands per platform.

## 2. Three-layer documentation for the apps

`apps/ios/CODE.md` and `apps/multiplatform/CODE.md` address the model
directly ("You are an expert developer for SimpleX Chat... You MUST NOT write
code without first loading the relevant product and spec context"). Their
stated reason: LLMs start each session with no understanding of the
codebase, and reconstructing behavior from flat source "wastes context window
and produces unreliable results". The docs are the persistent memory.

| Layer      | Contains                                                    | Answers                     |
|------------|-------------------------------------------------------------|-----------------------------|
| `product/` | concepts, user flows, views, business rules, glossary, gaps | What does it do and why?    |
| `spec/`    | technical design, API contracts, DB schema, services        | How is it built?            |
| source     | Swift / Kotlin app code and the Haskell core                | What does it execute?       |

Together the iOS and multiplatform `product/` and `spec/` trees are about
17,700 lines.

Linking between layers:

- `product/concepts.md` maps every concept to its product docs, spec docs,
  source files and tests. It is the entry point for every change.
- Product views and flows carry a "Related spec:" line; glossary and rules
  link down to spec.
- Spec docs carry "Source:" headers and function links with line ranges in
  the URL fragment (`[fn()](path.swift#Lxx-Lyy)`), with no line numbers in
  the display text, so a line shift means editing only the URL.
- `spec/impact.md` maps each source file to the product concepts it affects.
- A Document Map at the end of `CODE.md` maps source to spec to product.

**Required reading order before any code:** concepts.md, then the product
views/flows and rules.md, then spec, then source ("source code is the ground
truth"), then `spec/impact.md` to find everything affected. Internal-only
changes start at spec.

**Change protocol.** A task is not complete until all three layers agree:

- Update spec on every code change: new functions, changed signatures,
  removed functions, and every affected `#Lxx-Lyy` reference.
- Update product docs when user-visible behavior changes.
- When files are added, update the spec index, the Document Map,
  `spec/impact.md` and `product/concepts.md`.
- Tag problems found along the way with `[GAP]` (also summarized in
  `product/gaps.md`) and improvement ideas with `[REC]`.

**Every rule carries a "Why:"** line, for example "Prefer exhaustive switch
statements over default cases. Why: default cases bypass compiler checks for
new enum cases and hide bugs."

## 3. Adversarial self-review until two clean passes

After code and doc changes, the agent reviews consistency within each layer
(no contradictions, no unreachable states, flows match views) and across
layers (every changed function is in spec, every behavior change is in
product, every link resolves, impact and concepts are current). It repeats
review-and-fix "until two consecutive passes find zero issues". Stated
reason: "LLM non-determinism means a single review pass may miss violations".
The same convergence rule applies to plans.

## 4. Plans in the repo before implementation

Non-trivial features, multi-step changes and architectural decisions get a
plan in `plans/` before implementation. Required sections: problem
statement, solution summary, detailed technical design, detailed
implementation steps. The plan must be consistent with `product/` and
`spec/` and say which documents it will affect.

In practice (114 files, about 26,000 lines, dated 2026-02 to 2026-10):

- Plans cover features, bug fixes (`fix-...`) and test coverage work.
- Size scales with the change: `2026-05-13-desktop-single-instance.md` is
  about 30 lines; `2026-05-07-simplex-chat-python-implementation.md` is
  2,348.
- Larger work is sometimes split into a product plan and an implementation
  plan (`...-server-roles-product.md` / `...-implementation.md`).

## 5. How well it holds up (observed)

- **Naming drift.** `CODE.md` requires plan names like `YYYYMMDD_NN.md`;
  actual files are `YYYY-MM-DD-slug.md`, and 13 are undated. A
  rule nobody enforces drifts even in a strict process.
- **Line links mostly resolve.** Of 1,019 `#Lxx-Lyy` links in `apps/ios/spec/`,
  7 point to files that no longer exist and 2 point past the end of their
  file. This checks targets exist, not that the line ranges are still right.
- **The Haskell core has no product/spec layers**; it relies on the shorter
  shared `CODE.md` and `PROJECT.md`.
- Not checked: commit history (shallow clone), so whether agents or humans
  wrote particular changes, and how often docs are updated alongside code,
  is unknown.

## Takeaways (opinion)

Cheap and broadly useful:

1. Write the agent rules into normal contributor docs and build `CLAUDE.md`
   from them with `@` imports, so humans and agents share one source.
2. Give each rule a "Why:" so the agent can generalize to cases the rule does
   not name.
3. Store a dated plan with fixed sections in the repo before non-trivial
   changes; it doubles as a decision log for later sessions.
4. Repeat self-review until two consecutive clean passes.
5. Explicit threat model per change for anything security-sensitive.

Expensive, use selectively: the full product/spec/impact system with line
references. It needs updates on every change and a large codebase to pay for
itself. Consider it once agents repeatedly get lost or miss affected areas;
a lighter version is a concepts table (concept to files and tests) plus an
impact map.
